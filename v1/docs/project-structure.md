# Project structure

How three well-known Go CLIs lay out their code, the layout the rewritten Plumber CLI takes from
them, how it loads `.plumber.yaml`, where its documentation lives, the real projects that check
`analyze`, and the order in which the rewrite lands. It answers
[getplumber/monorepo#684](https://github.com/getplumber/monorepo/issues/684).

The new CLI is written from scratch under `v1/`, `main` included, and imports nothing from the
packages at the repository root. The old code is read as a reference and deleted once the new
binary passes the whole suite. The suite (`v1/test`) runs the built binary and never imports a
package, so it can judge both binaries with the same golden files.

## Comparison

Read at kubernetes [v1.37.2](https://github.com/kubernetes/kubernetes/tree/v1.37.2), helm
[v4.3.2](https://github.com/helm/helm/tree/v4.3.2) and golangci-lint
[v2.15.0](https://github.com/golangci/golangci-lint/tree/v2.15.0). For kubernetes, the CLI is
`kubectl`, whose code lives in `staging/src/k8s.io/kubectl`.

| | kubernetes (kubectl) | helm | golangci-lint |
|---|---|---|---|
| `main` | `cmd/kubectl/kubectl.go`: builds the root command, runs it, prints the error. | `cmd/helm/helm.go`: `NewRootCmd(os.Stdout, args)`, then maps a `CommandError` to its exit code. | `cmd/golangci-lint/main.go`: fills a `BuildInfo` (version, commit, date) and calls `commands.Execute(info)`. Exit codes live in `pkg/exitcodes`. |
| Commands | One package per command: `pkg/cmd/version`, `pkg/cmd/get`, … (about 40). | One flat package, `pkg/cmd`, one file per command (`version.go`, `install.go`, …). | One flat package, `pkg/commands`, one file per command. |
| Command wiring | `NewCmdVersion(f Factory, streams IOStreams)`, an `Options` struct, then `Complete`, `Validate` and `Run`. The `Factory` hands out clients. | `newVersionCmd(out io.Writer)` and a private `versionOptions` with a `run(out)` method. The work itself is in `pkg/action`, which knows nothing of cobra. | `newVersionCommand(info)` returns a `versionCommand` struct that holds the `*cobra.Command`, its options and its dependencies. |
| `pkg/` vs `internal/` | `pkg/` is public on purpose: other projects import kubectl's packages. `.import-restrictions` and `import-boss` check who imports what. | Mostly `pkg/` (22 packages), a public SDK used by other tools. `internal/` holds 16 packages. | `pkg/` for nearly everything, `internal/` for 4 helpers. The code is not meant as a library. |
| Domain code | Outside the commands: `pkg/describe`, `pkg/drain`, `pkg/explain`, … | `pkg/action` (one type per operation), `pkg/chart`, `pkg/kube`, … | One package per linter, `pkg/golinters/<name>`, each with its own `testdata/`. Output formats in `pkg/printers`. |
| Configuration | kubeconfig, loaded by client-go. | Settings come from environment variables and flags, gathered in `pkg/cli` (`environment.go`). | Viper reads `.golangci.yml` into hand-written structs (`pkg/config`). A checked-in JSON Schema (`jsonschema/golangci.jsonschema.json`) describes the file, and `config verify` validates it with `santhosh-tekuri/jsonschema` v6. |
| Tests | Unit tests next to the code. Black-box tests of the binary are shell scripts in `test/cmd`. | Unit tests next to the code. `pkg/cmd` tests are tables of `cmdTestCase` with a `golden` file in `pkg/cmd/testdata/output`, through `internal/test`. | Unit tests next to the code. `test/` runs the built binary on `test/testdata`, and each linter has an integration test next to it. |
| Docs | `cmd/gendocs` generates the kubectl reference from the cobra tree. | `helm docs` generates the reference from the cobra tree. | A Hugo site in `docs/`, partly generated by `scripts/website`. |

What Plumber takes:

- A thin `main` that builds the build info, runs the root command and maps an error to an exit
  code, like helm and golangci-lint. Plumber has four exit codes (0, 1, 2, 3) and the suite checks
  each one.
- An options struct per command, and the work outside the command package, like helm's
  `pkg/cmd` and `pkg/action`. Cobra stays in the command packages.
- One package per command group, like kubectl. Plumber has eight top-level commands, but `analyze`
  and `config` are big enough that a flat package would grow back into today's `cmd/`.
- A small `pkg/` for a named consumer, as helm and kubectl have, and `internal/` for the rest.
  Plumber's consumer is the platform backend (see [Public API](#public-api)).
- Import rules checked by a tool, as kubernetes does with `import-boss`: here, `depguard` in
  `v1/.golangci.yml`.
- golangci-lint's configuration: viper, hand-written structs, a checked-in JSON Schema and a
  validator (see [Configuration](#configuration)).
- [go-git](https://github.com/go-git/go-git) to read a repository the same way on GitHub and
  GitLab, cloned in memory (see [Repository access](#repository-access)). None of the three
  projects above needs this; it comes from what Plumber analyzes.
- Golden files next to the unit tests, like helm, and the black-box suite in `v1/test`, like
  golangci-lint's `test/`.
- A reference generated from the cobra tree, like kubectl and helm, so the docs can't drift from
  `--help`.

What it leaves:

- kubectl's `Factory`. It exists to hand out Kubernetes clients and REST mappers. Plumber has two
  providers and passes them as plain values.
- kubectl's `Complete`/`Validate`/`Run` split as a fixed rule. A command that has nothing to
  complete doesn't need the method.
- golangci-lint's command structs that hold the `*cobra.Command`. A function that returns the
  command is enough.

## Current state

Why the code is rewritten and not moved:

- `cmd/` is one package of 155 files and about 51,000 lines, tests included. It mixes the cobra
  commands, the output renderers (csv, ocsf, sarif, glsast, the legacy JSON) and the whole
  `analyze` run. `cmd/analyze_gitlab.go` alone is 2,370 lines.
- Flags are package-level variables (about 60 in one `var` block of `cmd/analyze_gitlab.go`), and
  11 `init` functions register commands and flags. A command can't be built twice in a test.
- The domain packages sit at the repository root and are all public: `control/`, `github/`,
  `gitlab/`, `configuration/`, `utils/`, `pbom/`, `capability/`, `provider/`, `finding/`,
  `policies/`, `defaultConfig/`. `internal/` holds 8 packages, chosen case by case.
- `utils/` collects unrelated helpers (git remotes, cache writes, image names, hashing).
- Each provider reads files through its own REST API (`github/github_workflows_remote.go`,
  `gitlab/rest.go`, `gitlab/ci_config.go`), and reading the remote of a local clone runs the `git`
  binary (`utils/gitremote.go`).
- Every policy reads one shared model, `ir.NormalizedPipeline` (`internal/ir`): 75 Rego policies
  read `input.pipeline`. Yet the user docs list only 8 controls on both providers, and 17 policies
  test the provider before doing anything. Each provider has to translate its configuration into a model
  that fits neither one.
- `analyze` resolves remote material and reads project settings on every run, so a token without
  enough rights shows up late, as settings reported unknown.
- Policy logic is tested from Go (19 Go test files in `policies/`). There is no `_test.rego` file,
  and nothing lints the Rego.
- The platform backend imports these packages, which were never designed as an API: it calls
  `gitlab.FetchGitlabFile` and `configuration.NewDefaultConfiguration` directly.
- No file describes `.plumber.yaml`. `configuration/schema.go` reflects a schema from the Go
  structs at run time, so an editor or a reviewer has nothing to read.
- The user documentation lives in another repository,
  [getplumber.io](https://github.com/getplumber/getplumber.io), and is kept up to date by hand
  (see [Documentation](#documentation)).

Moving these files under a new tree would keep every one of these problems.

## Target layout

```
v1/
  cmd/plumber/main.go        build info, run the root command, exit code
  pkg/                       the API the platform imports (see Public API)
    config/                  the .plumber.yaml model, Load, Validate, defaults
      plumber.schema.json    the static model, embedded with go:embed
    catalog/                 controls, issue types, score letter
    identity/                finding identity
    gitlab/                  fetch and parse a GitLab project, as the platform's snapshot worker does
  internal/
    cli/                     cobra and viper flags only: the root command, global flags, exit codes
      analyze/               one package per command group, each with an options struct
      capabilities/
      catalog/
      config/
      explain/
      version/
    preflight/               checks the token and rights the chosen options need
    gitrepo/                 go-git: open a local clone, clone a remote in memory at a ref, read files
    provider/
      github/                parse, resolve and read settings; model/ holds the typed workflow
      gitlab/                the same for GitLab, on top of pkg/gitlab; model/ holds the typed CI config
    control/                 selects controls and runs OPA
      policies/              embedded Rego (see Policies)
        .regal/              Regal config
        schemas/             input schemas for opa check --strict
        github/ gitlab/      one policy set per provider, each policy with its _test.rego and testdata/
        lib/                 Rego functions both sets share, with their tests
    finding/                 findings and attack paths
    score/                   the score and its gates
    output/                  one package per format
      json/ csv/ sarif/ ocsf/ glsast/ pbom/ text/
    publish/                 score push, platform push, MR comment, badge
    tools/gendocs/           builds the docs bundle (see Documentation)
  docs/
    user/                    the user guides, published on getplumber.io
  test/                      the black-box suite, unchanged
```

The exact package names, whether preflight is a package or a method of each provider, and whether
`score-compare` gets a home are settled as each part is rewritten. The tree fixes the shape only.
[analyze-flow.md](analyze-flow.md) shows how these packages work together in a run of `analyze`.

There is no provider-neutral pipeline model. Each provider parses its own document, typed against
its official schema (SchemaStore's `github-workflow.json`, GitLab's `ci.json`) and expanded
(GitLab's `extends`, `default`, `!reference` and includes), with the file and line of every node.
Its policies read that document directly, and the controls both providers have call the same
functions in `policies/lib`. Findings, the score and the attack paths are shared.

Rules for the new code:

- Nothing under `v1/` imports `github.com/getplumber/plumber/{cmd,control,github,gitlab,…}` or the
  root `internal/`. A `depguard` rule in `v1/.golangci.yml` fails the lint when it does.
- Only `internal/cli/...` imports cobra and binds flags and environment variables in viper. The
  other packages take their inputs as arguments and write to an `io.Writer`, so a unit test calls
  them directly.
- Only `pkg/config` reads `.plumber.yaml`.
- Only `internal/gitrepo` imports go-git, and no package runs the `git` binary.
- A policy reads its own provider's document; logic two providers share goes in `policies/lib`.
- Rego follows the Rego style guide, passes Regal, and is tested in Rego (see [Policies](#policies)).
- No package-level state: no flag variables, no `init` that registers anything. The root command
  is built by a function, so a test can build it many times.
- An error that ends a command carries its exit code (one type in `internal/cli`), and `main` is
  the only place that calls `os.Exit`.
- Each package has its unit tests and its `testdata/` next to it. Golden files of unit tests use
  one helper; the black-box suite keeps its own copy, as rule 5 of [AGENTS.md](../AGENTS.md) says.

## Configuration

The static model of `.plumber.yaml` is `v1/pkg/config/plumber.schema.json`, a JSON Schema (draft
2020-12) file that is checked in and reviewed like code. Every key has its type, description,
enum and default, and every object sets `additionalProperties: false`. The CLI, the platform, the
editors (through `# yaml-language-server: $schema=…`) and the docs all read this one file.

The Go types in `pkg/config` are written by hand. A parity test walks the structs and the schema
and fails when a field and a property differ in name, type or presence.

Loading happens in four stages:

1. Parse the YAML and validate it against the schema with `santhosh-tekuri/jsonschema` v6. This
   catches unknown keys, wrong types and keys in the wrong case. It runs before viper because
   viper ignores key case, and the keys of `.plumber.yaml` are camelCase.
2. Viper layers the sources, lowest first: the built-in default config, `extends`, the file,
   `PLUMBER_*` environment variables, flags.
3. `UnmarshalExact` into the Go types.
4. Checks the schema can't express, such as required expressions.

Tests, besides the parity test:

- The embedded default config validates against the schema.
- Every config in `v1/test/local/testdata/inputs` validates, or fails the way its golden expects.

## Repository access

The content of a repository comes through [go-git](https://github.com/go-git/go-git), the same way
on GitHub and GitLab: the CI files, the local includes, the workflow files, the files a control
reads, and the remote actions, reusable workflows, includes and components of other projects.

- A remote repository is cloned at the ref to analyze (a branch, a tag or a commit), with depth 1
  and a single ref, into memory storage (`memory.NewStorage()`). There is no worktree: files are
  read from the commit's tree, and nothing is written to disk.
- A run caches each clone, so a project referenced many times at the same ref is cloned once.
- Other projects are cloned only with `--resolve-depth`, and the settings APIs are called only with
  `--sanity`. By default a run reads the target's own files and nothing else.
- A local run opens the clone on disk with go-git (`PlainOpen`) to read its remote, branch and
  `HEAD`. The `git` binary is not needed.
- HTTPS clones authenticate with the provider token.
- The provider APIs stay for what git doesn't carry: branch protection, project settings, CI/CD
  variables, merge request approvals, security policies, and GitLab's merged CI configuration when
  a control needs the server's view of it.

The rewrite starts on go-git v5 (v5.19.3 is the latest stable on 2026-11-19) and moves to v6 when
it is final; v6.0.0-beta.1 is out. Filtered fetch (`blob:none`), which go-git lists as partly
supported, would cut the memory a large repository needs.

The risk is the size of a depth-1 clone held in memory for the largest projects, such as
gitlab-org/gitlab and nodejs/node. The reference harness measures it for each project and records
it in this section. If a clone is too large, `gitrepo` reads the CI files through a sparse or
filtered fetch, or uses the API for that repository.

## Policies

The Rego policies follow the [Rego style guide](https://github.com/open-policy-agent/rego-style-guide),
and [Regal](https://github.com/open-policy-agent/regal) enforces it.

- Regal reads `.regal/config.yaml` at the root of `control/policies/`, with every rule on. A rule
  turned off in the config, or an inline `# regal ignore:<rule>`, names one rule and says why, like
  a `//nolint`.
- Files are formatted with `opa fmt` (Rego v1 syntax) and pass `opa check --strict`.
- A package matches its directory: `plumber.github.<control>`, `plumber.gitlab.<control>`,
  `plumber.lib.<topic>`.
- Each policy declares its input schema in `# METADATA`, as the style guide suggests: SchemaStore's
  `github-workflow.json` or GitLab's `ci.json`, extended with what the CLI adds (source locations,
  resolved imports, `settings`). The schemas live in `control/policies/schemas/`, so
  `opa check --strict` fails a policy that reads a field the provider doesn't have.
- Every rule that raises a finding has metadata annotations: title, description, and custom fields
  for the ISSUE code, the control key and the severity. The catalog step decides whether
  `pkg/catalog` reads the codes from these annotations instead of from Go.

Policies are tested in Rego, never from Go:

- Each policy has a `_test.rego` next to it. Its `test_` rules feed small provider documents from
  the policy's `testdata/` with `with input as`.
- Every rule has at least one case that raises its finding and one that doesn't.
- `opa test --coverage` reports the coverage, and the target fails below the minimum the first
  policy PR sets.
- Go tests check only the wiring: the embed, the loading, and how an OPA result becomes a finding.

opa and regal are pinned binaries: the make targets download them into `v1/bin` (not committed),
and CI installs them with `open-policy-agent/setup-opa` and `setup-regal` pinned by SHA. Nothing is
added to go.mod for them. The opa binary has the version of the OPA library that go.mod requires
(v1.21.2 today), so the tests run on the evaluator the CLI embeds. On 2026-11-19 the latest
releases are opa v1.22.4 and regal v0.43.0.

The first policy PR adds the config, the schemas, the binaries and these commands:

- `make -C v1 lint` also runs `regal lint`, `opa fmt --list` (it fails on any file to format) and
  `opa check --strict`.
- `make -C v1 test-rego` runs `opa test --coverage`.
- `v1.yml` runs both, with the new actions pinned by SHA and `actions.lock` regenerated.

## Documentation

The CLI's user documentation moves from [getplumber.io](https://github.com/getplumber/getplumber.io)
to this repository, and this repository generates what the site renders. Today the site holds,
all maintained by hand:

- 8 MDX pages in `src/docs/data/docs/en/cli/`, about 3,900 lines: `index`, `installation`,
  `configuration`, `controls-configuration` (1,205 lines, every field of every control),
  `how-the-analysis-works`, `reference/index` (697 lines, with a hand-written flag table),
  `github/index` and `gitlab/index`. They use the site's `Aside`, `Tabs`, `Steps`, `Badge` and
  `Icon` components.
- `src/data/issues.ts` (4,876 lines), copied from `control/codes.go`. It drives the
  `/docs/[section]/issues/[code]` pages. Each issue has a `ProductScope` of `all`, `cli` or
  `platform`.
- `src/data/controlIds.ts`, copied from `configuration/registry.go`.

Sources in this repository:

- Guides in `v1/docs/user/`, in plain Markdown with front matter (title, description, sidebar
  order), so they also read well on GitHub. GitHub alerts (`> [!NOTE]`) stand for `Aside`, and the
  site maps them with a remark plugin. Per-provider content follows a heading convention, settled
  in the docs import step, that the site turns into its provider tabs.
- Contributor docs, like this file, stay in `v1/docs/`.

Generated references, in JSON:

| File | Built from | Replaces on the site |
|---|---|---|
| `commands.json` | the cobra tree: commands, flags, defaults, deprecations, exit codes | the flag tables of `reference/index.mdx` |
| `config.schema.json` | `pkg/config/plumber.schema.json`, as is | the field tables of `controls-configuration.mdx` |
| `issues.json` | the catalog: codes, titles, descriptions, severity, remediation, examples | `issues.ts` for the `all` and `cli` scopes; platform-only issues stay on the site |
| `controls.json` | the catalog: control keys, ids, providers, issues raised | `controlIds.ts` |

`internal/tools/gendocs` builds the bundle, like kubectl's `cmd/gendocs`, so the shipped binary
doesn't carry it. `make -C v1 docs` writes it to `v1/docs/dist/` (not committed). A test fails when
a command, a flag or a schema key has no description, and a golden of `commands.json` shows every
change of the CLI surface in review.

Each CLI release attaches the bundle, `plumber-docs-<version>.tar.gz`: the guides, the JSON files
and a `manifest.json` with the version and the file list. The site pins a CLI version, fetches its
bundle at build time and renders it with its own components, so the published docs always match a
released CLI. Moving the pin is a site PR. Until the switch step, `v1.yml` only builds the bundle
as a CI artifact, because attaching it to a release means editing `release.yml`, outside `v1/`.

The harness is `v1/test/corpus`, a third package with the `corpus` build tag. Like the other two,
it has only `_test.go` files and its own copy of the code they share (rule 5 of
[AGENTS.md](../AGENTS.md)). `TestGitHubCorpus` and `TestGitLabCorpus` have one row per project.
Each row analyzes the project at its pinned ref with both binaries (`-o report.json`), normalizes
both reports as the e2e rows do, and diffs them. The old CLI is the oracle while it exists. A
difference fails the row unless `testdata/expected/<provider>/<row>.yaml` lists it with its reason,
such as an inventory decision or a bug of the old CLI. After the switch, the last agreed reports
become `testdata/golden/<provider>/<row>.yaml` and the rows compare against them.

The corpus needs `GITHUB_TOKEN` and `GITLAB_TOKEN`, and a run costs far more API requests than the
e2e suite. Its rows run one at a time with the e2e retry rules. It never runs on a PR: run
`make -C v1 test-corpus` (or `test-corpus-github`, `test-corpus-gitlab`) by hand before an analyze
step merges. A daily run waits for monorepo#651, like the e2e suite.

The new CLI clones the pinned commit itself through `internal/gitrepo`, so its side of a row
analyzes exactly that commit. The harness step settles how the old binary is pinned: it checks
whether `--branch <tag>` works on both providers, and whether a run inside a shallow clone with a
token reads the checked-out files or the default branch through the API. The harness also records
the in-memory clone size of each project (see [Repository access](#repository-access)).

## Rewrite order

Each step is one issue and one PR against `release/v1`, added to
[#640](https://github.com/getplumber/monorepo/issues/640) as its own step. Every step:

- keeps `make -C v1 test-integration` green, and the e2e target of each provider it touches;
- applies the decisions of [feature-inventory.md](feature-inventory.md) for the commands it
  rewrites, and explains each golden change in its PR;
- adds the commands it rewrites to `commands.json`, and updates the guides they appear in;
- reads the old code on `release/v1` as it is after the last sync from `main`. A sync that changes
  a behavior turns its rows red for both binaries until the new code follows.

The steps:

1. Skeleton: `v1/cmd/plumber` with the root command, `version` and the exit-code type, plus the
   `depguard` rule. The suite builds both binaries and each test picks one; `TestRoot`'s version
   and unknown-command rows switch to the new one. This step also settles the `cli` build tag:
   today every file in `v1/` has it, and the new production code should not need it. The `scope`
   job of `v1.yml` starts accepting additions to go.mod and go.sum (rule 2 of
   [AGENTS.md](../AGENTS.md)), which the new dependencies need.
2. Config model: `pkg/config/plumber.schema.json` for the current keys of `.plumber.yaml`, with the
   inventory's decisions, the Go types, the parity test and the validation. No command reads it
   yet.
3. Docs import: the 8 site pages copied to `v1/docs/user/` as Markdown, and `gendocs` with
   `config.schema.json`. The site keeps its copy until the site switch.
4. `completion`, `catalog`, `capabilities`: commands with no input but the embedded catalog.
   `pkg/catalog` gets the registry and the metadata of each control, without their checks, and
   `gendocs` adds `issues.json` and `controls.json`. The platform moves from `control` and
   `capability` to `pkg/catalog`.
5. `explain`: reads the catalog and the attack paths.
6. `config`: viper loading in `pkg/config` (the four stages, `extends`, migrate) and the
   subcommands, with the merges and removals the inventory decides (`resolve` into `view`). The
   platform moves from `configuration` and `defaultConfig` to `pkg/config`.
7. `score-compare`, or its removal if the inventory's decision holds.
8. `analyze` input handling: flags, target resolution, the ref to analyze (branch, tag or
   commit), `--resolve-depth`, `--sanity`, preflight, and the usage errors that `TestAnalyze`
   checks before any request. [analyze-flow.md](analyze-flow.md) is the design.
9. Reference harness: `v1/test/corpus` with the 10 rows of
   [Reference repositories](#reference-repositories), run with the old binary on both sides. That
   run proves the normalized reports are deterministic; the OCSF report differed between two runs
   in #688. It also measures the in-memory clone size of each project.
10. GitLab provider, one stage at a time:
    - static: `internal/gitrepo` (if the GitHub provider hasn't brought it yet), `pkg/gitlab`,
      the typed model and its expansion, then `policies/gitlab` one control family per PR;
    - resolve: remote, project and component includes;
    - sanity: the settings, with their policies.

    The first policy PR of steps 10 and 11 brings the Regal config, the schemas, the pinned opa
    and regal binaries, their make targets and the CI job (see [Policies](#policies)).

    Each PR switches the `TestGitLabIssue*` rows of its controls to the new binary, passing
    `--resolve-depth` or `--sanity` where the row needs them. `pkg/identity` comes with the first
    findings. The platform moves from `gitlab` and `finding/identity`.
11. GitHub provider: the same stages for GitHub (actions and reusable workflows in resolve;
    protection, rulesets and settings in sanity) and `TestGitHubIssue*`.
12. Outputs: one PR per format (json, csv, sarif, ocsf, glsast, pbom), each with its offline rows.
13. Switch: the release build and the integrations (`action.yml`, `templates/plumber.yml`,
    `Dockerfile`) use `v1/cmd/plumber`, releases attach the docs bundle, the suite drops the old
    binary, and the old packages are deleted. This step changes paths outside `v1/`, so it needs
    its own decision on rule 2 of [AGENTS.md](../AGENTS.md) before it starts.
14. Site switch, in getplumber.io: the site loads the bundle of a pinned release, deletes the moved
    pages, the CLI part of `issues.ts` and `controlIds.ts`, and redirects the URLs that change.

Every PR of steps 10 to 12 runs the corpus target of its provider and lists each new expected
difference in its description.

Steps 10 and 11 can run in either order, and 12 can start as soon as one provider is done. The new
layout is done when step 13 merges with no regression caught by the suite or the corpus, and the
docs move is done with step 14.
